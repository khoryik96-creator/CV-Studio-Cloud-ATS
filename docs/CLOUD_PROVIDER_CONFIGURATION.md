# M1 centralized AI configuration
Initial DeepSeek-only tenant configuration, using the existing AES-256-GCM envelope encryption and PostgreSQL RLS. Administrative status contains only revision, provider, model and enabled flag. Active owner/admin authorization is verified from the database; optimistic revision checks prevent stale updates; disabling clears the live credential columns without resetting revision. Physical backups and previous MVCC pages may retain ciphertext until normal retention/maintenance. No plaintext in database rows or status.

The worker resolver is directly compatible with WorkerRuntime(resolve_provider=service.resolve) in PR #17. Approved price/limit policies and encryption keyring must be injected by the trusted deployment composition root; no assumed current provider prices, user-supplied pricing, arbitrary URLs or automatic provider fallbacks. Credential decryption occurs just before each dispatch, with revision/role/activity checks; a configuration change prevents a subsequent dispatch under the old snapshot. A request already in flight cannot be recalled. If dispatch is denied after a budget reservation, existing fail-closed accounting conservatively retains the hold for reconciliation.

This internal service has no HTTP endpoints or production grants. Separate least-privilege worker/admin DB roles and key access, authenticated settings endpoints, CSRF, rotation/reconciliation procedures, secret-manager injection, admin audit history, approved real model catalogue and live synthetic-provider verification remain gates. Only synthetic test secrets; do not paste actual keys into GitHub or chat. No other providers until their transports and billing policies are implemented and tested.
