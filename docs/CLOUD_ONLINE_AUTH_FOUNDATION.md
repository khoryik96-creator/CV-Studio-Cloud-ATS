# Online CV Studio — authentication foundation (not a public release)

Target: https://cvstudio.hyplug.co. Leave the current fictional staging service
and the HyPlug project, Caddy and database untouched. This branch implements
an auth-only factory and internal WSGI entrypoint; it does not expose the UI,
document routes or live providers. Production readiness intentionally returns 503.

## Trust and provisioning
Use a new CV Studio Compose project, isolated network and separate PostgreSQL
database named cvcloud_online. Do not reuse the fixture or HyPlug database.
The future DB service name is online-db; create a non-owner cvcloud_auth
LOGIN role without role memberships or privileged attributes and a generated
password. Apply 001_auth.sql and 004_auth_epoch.sql as a separate schema owner,
then online_auth_grants.sql. Only the owner/controlled provisioning process
may create users; no default accounts, known fixture passwords or public
registration. Keep the password in a restricted mounted file, not Git or
command-line arguments. The auth role can read authentication records and
write sessions/rate limits but cannot directly modify users or tenants.
The narrow security-definer account lock must be owned by the schema owner.

Configuration: CVCLOUD_PUBLIC_ORIGIN=https://cvstudio.hyplug.co,
CVCLOUD_TRUSTED_PROXY_IP=<actual dedicated ingress peer IP>,
CVCLOUD_AUTH_PASSWORD_FILE=<absolute secret mount path>.
The factory refuses direct traffic and ambiguous forwarded IPs. The future
WSGI server must preserve the raw socket peer and forwarding headers for
this middleware. Caddy must overwrite X-Forwarded-For and X-Forwarded-Proto
with the actual client and HTTPS scheme, preserve the exact Host, and connect
through an isolated network with a fixed/verified peer; never trust arbitrary
forwarded headers or publish a backend port. No change to existing Caddy
routes until a reviewed candidate, TLS validation and rollback plan exist.

## Operator-only owner bootstrap and internal server

Build the auth-only image from the repository root using
`docker build -f cloud/deploy/Dockerfile.online-auth -t cvcloud-online-auth:local .`.
Do not run it on the current VPS yet. The future isolated Compose database
must be created with a separate, non-superuser LOGIN schema owner named
cvcloud_schema_owner. That role owns the cvcloud schema, applies the two auth
migrations and the restricted auth grants. No secrets or credentials are
generated by the image itself. The database hostname is online-db. Never
connect this image to HyPlug or the synthetic fixture database.

From a dedicated, interactive one-off operator container on that internal
database network, mount the schema owner password file read-only and set
CVCLOUD_SCHEMA_PASSWORD_FILE to its absolute path. Invoke
`python -m cloud.deploy.online_owner --tenant hyppies --email YOUR_EMAIL`.
Choose a unique strong owner password of at least 16 characters at the
hidden prompt; the confirmation must match. The operation refuses existing
organisation slugs, unexpected database/roles and fixture markers. No
password is printed or passed as an argument. Remove the one-off container
and its schema-owner secret mount afterward. The web container must never
receive that secret.

The auth-only image starts Waitress with the previously documented runtime
secret and exact proxy IP. Its listener is internal only, on port 8000;
no host port publication or existing Caddy edits are authorised. Incoming
forwarded headers are preserved for the immediate-peer middleware, not
trusted by Waitress. The listener limits body/header sizes, connection count
and threads. The production readiness endpoint stays 503, and neither the
original UI nor document processing routes are enabled. No live deployment
approval is implied by this image or successful auth tests.
